# SC-002 Integridad e identificadores de base de datos

Fecha: 29/10/2026. Rama solicitada: `SC-002`. Base local inspeccionada: `694a658`.
Equivalencia: CR-TEC-002 / TEC-002. Alcance transversal a horarios, feriados y motivos.
Clasificación principal: preventivo. Prioridad: alta. Estado: evaluación y plan documentados; publicado en PR en borrador; revisión humana pendiente.

## Solicitud, necesidad y origen

Consolidar IDs, claves y referencias mediante las migraciones existentes, completando la validación y el despliegue únicamente en un destino autorizado. No repetir el despliegue previo PostgreSQL ni limpiar datos por el solo hecho de documentar esta solicitud.

El origen es el diagnóstico técnico de esquema y perfilado de TEC-002. Francisco Kadin Valera Lizarraga coordina BD. El solicitante formal del área usuaria y la persona que acepta el resultado se deben confirmar. El perfilado del 18/10 es evidencia histórica y no certifica la instancia actual.

Beneficios: prevenir colisiones de ID, rechazar referencias inválidas y reducir dependencia de validaciones del aplicativo. Sin completar las garantías declarativas, los bloqueos de un repositorio no evitan todas las escrituras inconsistentes de otros procesos.

## Alcance y límites

Reutilizar perfilado, fixture, migración de integridad/IDs, aserciones y rollback existentes. La spec y el contrato abarcan Horario, RRHH_Feriado y Motivo_Perm; el ensayo de migración incluye también TipoPermiso para sus dependencias, totalizando cuatro PK/identidades según la evidencia. Las ocho FK se limitan al inventario verificado por TEC-002.

Conservar IDs y compatibilidad de consumidores; identidad BY DEFAULT y RETURNING según contrato. Perfilado/ensayos en copia QA ficticia. No deduplicar, borrar, restaurar o migrar el servidor compartido sin destino y alcance autorizados. No extender el trabajo a todo el esquema ni dar por actualizados los datos de la instancia con base en un registro antiguo.

## Impacto y riesgos

| Área | Impacto | Riesgo / medida |
|---|---|---|
| Funcionalidad | Altas, edición y borrado de horarios, feriados y motivos dependen de claves y referencias | Comprobar compatibilidad de los tres consumidores antes de desplegar |
| SQL | BD/diagnostics/tec002_profile.sql y migración 20261018_02_integrity_ids.sql | Precondiciones deben abortar ante duplicados, nulos o huérfanos, sin corrección destructiva implícita |
| Esquema | Cuatro PK/identidades, ocho FK y fecha única de feriado según ensayo | Contrastar inventario real y objetos preexistentes |
| Código | Repositorios Asistencia/Permisos que consumen default/identidad y RETURNING | Escritores con IDs explícitos pueden desalinear secuencias; ensayar transición |
| Datos | Conservar filas/IDs y generar nuevos valores sin colisión | Saneamiento exige decisión separada, copia y criterio de conservación |
| Pruebas | Fixture, aserciones, repetición, concurrencia, precondiciones y restauración | Un ensayo local aprobado no certifica servidor ni backup recuperable |
| Mantenibilidad | Contrato de datos explícito y scripts versionados | Mantener runbook, esquema compatible y responsabilidad de operación |

Riesgos técnicos: bloqueo durante DDL, dependencias no inventariadas, diferencias de versión PostgreSQL, objetos preexistentes, secuencias y rollback no diferencial. Una reversión estructural no debe retirar sin análisis objetos que ya existían en el destino.
